面试题：
1. try / except / else / finally 各自适合放什么逻辑？else 为什么不应简单用 try 内的最后几行替代？
try 放可能发生异常、且当前代码准备处理的最小范围操作，例如打开或解析文件。
except 接收抛出的异常，并做异常管理
else 只在 try 没有异常时执行；它的价值是把不应被捕获的后续逻辑放在 try 外
finally 是就算出现异常，最后也应该执行的代码，常用于清理资源；但通常文件资源优先交给 with 管理。
else 不应简单塞进 try 的最后几行，因为那些后续代码自身出现的 Bug 可能被 except 误捕获，造成“看起来像文件读取失败”，实际却是后续逻辑错误。try 范围应尽量小。
2. 什么情况下应该捕获异常后处理，什么情况下应该继续抛出异常？
捕获异常后处理：当前层能合理恢复时捕获。例如读取可选配置文件：文件不存在时使用默认配置；网络请求临时失败时有限次数重试。
继续抛出异常：当前层无法恢复，或调用方需要知道失败原因时，应继续抛出。例如训练数据标签文件不存在、格式损坏时，不应悄悄返回空数据集，否则训练流程可能在错误数据上继续运行。可以补充上下文后重新抛出异常，但不要吞掉异常。
3. 为什么读写文本文件时应显式指定 encoding="utf-8"？不指定可能出现什么问题？
文本文件保存的是字节，读取时必须按某种编码把字节解码为字符串。若不指定编码，Python 会使用操作系统默认编码；同一份代码在不同系统上可能使用不同默认值。
当文件实际编码与读取编码不一致时，可能出现 UnicodeDecodeError，也可能产生乱码。写文件同样要显式指定 UTF-8，保证跨平台行为一致。
4. with open(...) as f 解决了什么资源管理问题？即使代码中 return 或抛异常，文件会怎样？
with 管理文件资源。离开 with 代码块时，无论正常执行、return，还是发生异常，文件对象都会被正确关闭；写入模式下也会进行必要的缓冲区刷新和关闭处理。
因此它能避免文件句柄泄漏、文件长期被占用、缓冲内容未及时写入等问题。
5. 直接写目标文件有什么风险？“写临时文件后再替换”为什么更安全？
直接用写模式打开目标文件时，旧内容通常会立刻被截断。若程序在写到一半崩溃、磁盘写入失败或内容校验失败，目标文件可能只剩半成品，原始正确文件也已经丢失。
