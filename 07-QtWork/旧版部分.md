# `PacketCodec`文件细节

```text
一个文件
 ├─ 多个 Chunk（例如每块 4 MB，便于线程任务和接收重组）
 │   └─ 多个 Segment（例如每包 60 KB，便于网络发送）
```

## 1. 所用包头的数据及其含义

| 字段 | 大小 | 含义 |
|---|---:|---|
| `m_nMagic` | 4 字节 | 魔数，例如 `0x51465450`，用来判断收到的是不是本协议的数据包 |
| `m_nVersion` | 2 字节 | 协议版本，后续升级协议时用于兼容判断 |
| `m_nMessageType` | 2 字节 | 包类型：元信息包、文件数据包、完成通知包等 |
| `m_nFeatureFlags` | 2 字节 | 标志位，例如是否为首分片、末分片、块开始或块结束 |
| `m_nHeaderLength` | 2 字节 | 包头长度；当前固定为 `64` |
| `m_oTransferId` | 16 字节 | 本次文件传输的唯一 ID，区分同时传输的多个文件 |
| `m_nChunkIndex` | 4 字节 | 当前是文件的第几个“块” |
| `m_nChunkCount` | 4 字节 | 文件总块数 |
| `m_nSegmentIndex` | 4 字节 | 当前是这个块里的第几个“网络分片” |
| `m_nSegmentCount` | 4 字节 | 当前块总共有多少个网络分片 |
| `m_nPayloadSize` | 4 字节 | 后面实际载荷 `arrPayload` 的字节数 |
| `m_nFileSize` | 8 字节 | 整个文件的总字节数 |
| `m_nChunkOffset` | 8 字节 | 当前块在原始文件中的起始字节偏移 |

## 2. 所用MetaData的数据及其含义

| 字段 | 含义 |
|---|---|
| `m_oTransferId` | 本次传输的唯一 UUID；用来区分不同文件或并发传输任务 |
| `m_strFileName` | 原文件名，例如 `video.mp4` |
| `m_nFileSize` | 文件总大小，单位是字节 |
| `m_nChunkCount` | 文件一共被切成多少个“块” |
| `m_nChunkSize` | 每块的大小，例如 4 MB |
| `m_nSegmentSize` | 每个块还会拆成多少字节的网络分片，例如 60 KB |

## 3. 拢共分的包的类型及原因

这三个 `MessageType` 是为了让接收端知道：收到的这个包到底是“文件说明”“文件内容”，还是“发送结束通知”。

一次文件传输不是只发一种包，而是一个完整流程：

```text
发送端                                      接收端

MetadataPacket  ───────────────────────→   创建本次接收会话、准备临时文件
ChunkPacket     ───────────────────────→   按位置写入文件数据
ChunkPacket     ───────────────────────→   按位置继续写入
ChunkPacket     ───────────────────────→   ...
CompletePacket  ───────────────────────→   检查是否完整，合并/保存文件
```

三个类型分别是：

| 类型 | 什么时候发 | payload 里装什么 | 接收端做什么 |
|---|---|---|---|
| `MetadataPacket` | 发文件前，只发一次 | `STransferFileMetadata` 序列化后的 JSON | 创建传输会话，知道文件名、总大小、总块数、块大小等 |
| `ChunkPacket` | 传输过程中，发很多次 | 真正的文件字节 | 根据包头的块号、分片号、偏移量写到正确位置 |
| `CompletePacket` | 所有数据包发送完成后，只发一次 | 通常没有实际文件内容 | 通知接收端发送方已结束，让它检查缺块、合并文件或报错 |

## 写入的细节点1：

`DataStream` 在序列化 `QByteArray` 时，不只写内容，还会先写长度,所以需要这样写，确保只写入的是内容

```cpp

```

# `AbstractTransferChannel`文件细节

## 写入的细节点1：

```cpp
class AbstractTransferChannel : public QObject
{
    Q_OBJECT

signals:
    void SignalPacketReceived(const QByteArray &arrPacket);
    void SignalLogMessage(const QString &strMessage);
};
```

只要这个类本身声明了 `signals`、`slots` 或 `Q_PROPERTY`，就必须在这个类里也写 `Q_OBJECT`。

## 写入的细节点2：

`explicit` 用来禁止“隐式类型转换”。

这个构造函数：

```cpp
explicit AbstractTransferChannel(
    const QString &strChannelName,
    QObject *pParent = nullptr
);
```

虽然有两个参数，但第二个参数有默认值，因此它可以只传一个 `QString`：

```cpp
AbstractTransferChannel(QStringLiteral("TCP"));
```

没有 `explicit` 时，C++ 会把它当作“可用于自动转换”的构造函数。类似下面这种意外写法可能被允许：

```cpp
void SetChannel(AbstractTransferChannel channel);

SetChannel(QStringLiteral("TCP")); // 编译器可能自动构造对象
```

加上 `explicit` 后，必须明确写出构造动作：

```cpp
SetChannel(AbstractTransferChannel(QStringLiteral("TCP")));
```

不过你的 `AbstractTransferChannel` 之后通常会有纯虚函数，它本身是抽象类，不能直接创建对象；这里加 `explicit` 更多是一种良好的接口习惯：

## 写入的细节点3：

```cpp
    /**
     * @brief GetChannelName
     * @param 无
     * @return 当前传输通道名称。
     * @details 用于统一输出 TCP/UDP 协议相关日志。
     */
    QString GetChannelName() const; //const 函数承诺不修改当前对象的成员状态。
```

## 写入的细节点4：


# `TcpTransferChannel`文件细节

## 1. 掌握知识点：父类继承的方式

因为 `TcpTransferChannel` 的直接父类不是 `QObject`，而是 `AbstractTransferChannel`。

类层级应是：

```text
QObject
  └─ AbstractTransferChannel
       └─ TcpTransferChannel
```

如果你的头文件是：

```cpp
class TcpTransferChannel : public AbstractTransferChannel
```

那么构造函数初始化列表只能直接初始化它的直接父类：

```cpp
TcpTransferChannel::TcpTransferChannel(QObject *pParent)
    : AbstractTransferChannel(QStringLiteral("TCP"), pParent)
{
}
```

不能这样：

```cpp
TcpTransferChannel::TcpTransferChannel(QObject *pParent)
    : QObject(pParent) // 错误：QObject 不是直接父类
{
}
```

C++ 规定：派生类只能在初始化列表中初始化“直接基类”；`QObject` 的初始化由 `AbstractTransferChannel` 自己负责。

## 2. `Q_OBJECT`的析构

```cpp
TcpTransferChannel::TcpTransferChannel(QObject *pParent)
    : AbstractTransferChannel(QStringLiteral("TCP"),pParent),
      m_pTcpServer(new QTcpServer(this)),//this 指向“当前正在创建的 TcpTransferChannel 对象”,可以辅助析构
      m_mapReceiveBuffer()
{
 //Todo
}
```

这里的：

```cpp
m_pTcpServer(new QTcpServer(this))
```

this 指向“当前正在创建的 `TcpTransferChannel` 对象”。

也就是说，它建立了 Qt 的父子对象关系：

```text
TcpTransferChannel（this）
└─ QTcpServer（m_pTcpServer）
```

`QTcpServer` 继承自 `QObject`，构造函数可以接收父对象：

```cpp
QTcpServer(QObject *parent = nullptr);
```

把 this 传进去后，`m_pTcpServer` 的父对象就是当前通道。以后析构 `TcpTransferChannel` 时，Qt 会自动析构这个 `QTcpServer`，不用手动：

```cpp
delete m_pTcpServer;
```

这也是 Qt 中常见的内存管理方式。

不用 this 时：

```cpp
m_pTcpServer(new QTcpServer)
```

也能创建，但没有父对象；你就必须自己负责释放，否则可能内存泄漏。

另外：

```cpp
m_mapReceiveBuffer()
```

只是显式调用 `QHash` 的默认构造函数，创建一个空 Hash 表。它可以省略，效果相同：

```cpp
TcpTransferChannel::TcpTransferChannel(QObject *pParent)
    : AbstractTransferChannel(QStringLiteral("TCP"), pParent),
      m_pTcpServer(new QTcpServer(this))
{
}
```

## 3. QTCPServer和QTCPSocket：

`QTcpServer` 和 `QTcpSocket` 的关系可以理解为：

- `QTcpServer`：负责“监听并接受连接”
- `QTcpSocket`：代表“某一条具体的 TCP 连接”，负责真正收发数据

例如接收端启动后：

```text
QTcpServer 监听 0.0.0.0:8899
```

发送端连接过来：

```text
发送端 QTcpSocket  ─────── TCP 连接 ─────── 接收端 QTcpSocket
                                                ↑
                                  由 QTcpServer 接受并创建
```

`QTcpServer` 本身不传文件；它只负责：

```cpp
listen(...);                 // 开端口等待连接
nextPendingConnection();     // 取出新连接对应的 QTcpSocket
```

真正的 `readAll()`、`write()`、`readyRead()` 都发生在 `QTcpSocket` 上。

## 写入的细节点2：

```cpp
pSocket->disconnect(this);
pSocket->close();
pSocket->deleteLater();
```

断开连接的这三步的作用分别如下：

- `pSocket->disconnect(this);`断开 `pSocket` 发给当前 `TcpTransferChannel` 的信号槽连接。
- `pSocket->close();`真正关闭这条 TCP 连接，断开对端。
- `pSocket->deleteLater();`安排 Qt 在下一次事件循环中删除 `QTcpSocket` 对象。

不用立即 `delete pSocket`，是因为它可能正处于信号槽调用过程中；延迟删除更安全，避免对象被立刻销毁后仍有代码访问它。
